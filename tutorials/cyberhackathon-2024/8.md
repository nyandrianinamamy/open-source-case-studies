# Exercise 8 (Sidetrack): ACSL specifications for greater good

This is more of a free-form exercise; there is no single right answer.

Files `8.c`, `8.h` and `8-user.c` implement a very simplistic file I/O API,
with operations such as `openf`, `closef`, `writef`, etc.

- `8.h` contains the public API;
- `8-user.c` contains some test cases, which call the API functions;
- `8.c` contains the implementation of the library, in a somewhat
  vulnerable state. This file is supposed not to be touched by the user (you).

## Task 1: Explore the test cases

By running Frama-C/Eva with both `8.c` and `8-user.c`, you can see that some
test cases are fine, while others raise some alarms.

Note: the volatile `nondet` variable, as well as the `if (nondet) {...}`
conditions in the `user_bad*` tests are used to allow Eva to reach all test
cases, even when one of them fails; otherwise, the analysis would stop as soon
a definite undefined behavior takes place.

## Task 2: Devise some easy hacks

(Some C skills required)

Hacking into this API is relatively simple; there are not many checks.
It should be relatively easy to add or modify some test cases to create
buffer overflows and modify the access rights to the `passwd` file.

Note that Frama-C will not necessarily help much when finding exploits;
being a tool used by "the good guys", Frama-C follows the semantics of the
C standard and cannot analyze what the actual implementation does when there
are undefined behaviors. For instance, whether a buffer overflow will overwrite
a given variable and allow the program to bypass some checks.

However, Frama-C does help ensure that a properly written code should be free
of buffer overflows.

## Task 3: Add ACSL specifications

Some informal specifications can be converted into formal ACSL annotations.
Such annotations have the advantage that Frama-C can use them (when there is
no available code) or check that the code respects them.

Function `openf` has some informal comments specifying what should be verified,
and also an example specification of how these properties are written in ACSL.

Note: a full ACSL tutorial is out of the scope of this hackathon. For a quick
guide, you can check the Appendix A of the
[Eva User Manual](https://www.frama-c.com/download/frama-c-eva-manual.pdf).

## Task 4: Use WP or other plug-ins

Once you have ACSL specifications for a function, you can use other Frama-C plug-ins, such as
WP, to prove their correctness. The main advantages of WP are:
- Proofs are valid for _all_ execution contexts;
- WP is _modular_, that is, you can specify and prove only a few important functions, and
  benefit from extra guarantees, even if all the code is not yet proven.

Frama-C is able to combine results. If Eva cannot prove the absence of undefined behaviors in
a given function, but WP can, then Eva can rely on WP's results and consider them proved.
