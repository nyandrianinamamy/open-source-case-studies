## Task 3: Alarm reachability

Often, an *Invalid* alarm means that there *is* a problem in the code; unlike
an *Unknown* alarm, which means *maybe*, Invalid means "when this statement is
reached, something will go wrong".

However, remember that Eva performs over-approximations: therefore,
"when this statement is reached" actually means
"*if* this statement is reached". In the general case, there is no way to know
whether a statement is actually reachable (at least, not without using other
plug-ins).

One way to check if such situations *do* happen is to test them. This does not
provide strong guarantees, but can help understand the analysis result, and
guide eventual changes.

For now, we will add a simple `printf` to print something just before reaching
the Invalid alarm. Use any phrase easy to grep, such as `BOOM`.

Recompile and re-run the program, then see if you get such a message.

Hint: use `grep` to filter the (verbose) output of `debie1`.

Do not read further until you finish this task.

## Task 5: Tainted memories

We will start using Eva's *Taint analysis* (still in experimental stage) to
try and detect undesirable behavior provoked by an attacker.

Unlike runtime errors, which are defined by the C standard and automatically
programmed in Frama-C, *taint analysis* requires the user to specify what is
"controlled by the attacker", that is, *tainted*.

This is done using the `//@ taint <variable>;` annotation.

In this exercise, we will assume the attacker, an evil AI capable of giving
false readings to input sensors, is able to corrupt the analog-to-digital
converters used in our satellite, by emitting carefully crafted electromagnetic
pulses.

### Task 5.1. Simulating the attacker

Since our code does not use *real* sensors, but emulates them using a
*test harness* (file `harness.c`), we will consider such data to be injected
in the `Start_Conversion` function, just after calls to `Next_Rand`.
That is, we will taint variable `ad_value` just after these instructions:

```
   ad_value = ((uint16_t)Next_Rand (&ad_rand_index)) << 8;
   ad_value |= (uint16_t)Next_Rand (&ad_rand_index);
```

Open your code editor and add the taint annotation to `ad_value`.

### Task 5.2. Checking for taints

We will now add annotations to help us check vulnerable parts of our program.
In each site, we will add an `//@ check !\tainted(<expr>);` annotation, where
`<expr>` is the memory contents we want to check for taints.

In other words, we want to assert that the given expression is *not tainted*.

Note: currently, the `\tainted` predicate only detects *direct* taints.
This may change in the future.

Add such an annotation just before the check that leads to the call to
`Self_Destruct`. We want to check if the contents of `limits->plus_5_voltage`
are tainted.

As an extra precaution, we will also check that the attacker cannot take
control of our satellite. The module `tc_hand.c` handles telecommand
operations. A self-destructing satellite is already bad, but a satellite under
full control of an evil AI is even worse.

There are a few functions with suggestive names, such as `UpdateTarget`, that
receive a `*command` as argument and read it to know what to do. Add checks
for each of these functions, to see if these commands are possibly under enemy
control.

### Task 5.3. Running the analysis with taint

We will now run the analysis, adding option `-eva-domains taint`.
If you already used that option to add other domains, then add `taint` to the
list, e.g. `-eva-domains equality,taint`.

At this stage, since the analysis takes about a minute, it might be better to
split it in two steps:

1. Run the analysis in the command line, saving its results;
2. Open Ivette and load the previous result.

To do so, instead of running `ivette`, run `frama-c` (with all the necessary
options), and add at the end `-save eva.sav`. This will run Frama-C + Eva,
spitting lots of messages in the terminal, and then it will save the
results in file `eva.sav`.

Then, you can simply run `ivette -load eva.sav` to open Ivette and load the
results.

### Task 5.4. Seeing taint with Ivette

The AST will now underline lvalues (an *lvalue* in C is an expression that can
be assigned to, such as a variable, an array cell, or a field in a struct)
that are *directly* or *indirectly* impacted by the tainted expression:

- a *direct* taint is propagated via assignments, e.g. `int a = b;` will
  taint `a` if `b` was tainted;
- an *indirect* taint is propagated whenever a conditional path is controlled
  by a tainted variable, e.g. if `b` is tainted, then
  `if (b) { a = 0; } else { a = 1; }` will propagate an indirect taint to `a`.
  This is because the value of `b` can be used to indirectly modify the value
  of `a`.

The *Properties* panel in Ivette can display taint information for each
property. Right-click on its header row and select "Taint" in the context menu.
A column with a paintbrush icon will appear. In it, a green, empty drop means
"untainted"; a gray drop means "*indirectly* tainted";
and a dark blue drop means "*directly* tainted". Hovering the mouse will
show a tooltip with this information.

Note: remember that Eva *overapproximates*; thus when it says "tainted", that
means "*possibly* tainted". But when it says "untainted", it is definitely
not tainted.

### Task 5.5. Understanding the origin of the problem

The taint analysis showed that our code is vulnerable to such attacks. Now we
need to better understand it in order to devise a protection, if we can.
In the worst case, we will at least be able to explain why it exploded.

We will use an Eva-derived plug-in, called *Studia*, which is integrated with
Ivette.

First, drag and drop the *Locations* component from the right-hand sidebar and

Then, navigate to the `!\tainted` check that has an *Unknown* status. You can
use the Properties panel to do so, filtering only Unknown/Invalid statuses,
or clicking on the Property column to sort by type. The only `check` properties
are those you added.

Now, in the AST, right-click the `limits->plus_5_voltage` in the statement
after the annotation, and use the menu item "Studia: select writes". This
will compute all statements in the code which write to that memory location.
Such statements will be added to the *Locations* panel
(which should have 5 entries).

Quickly inspect the locations. The function names are helpful. One of them
initializes the memory location, while the others copy the data from the
analog-to-digital converter.

Most importantly, *there are no other instructions that write to that memory*.

Can you propose simple code changes to prevent the `plus_5_voltage` field from
being tainted?

### Task 5.6. Protecting the unprotectable

In general terms, our attacker is too strong. Injecting arbitrary data in the
analog-to-digital converters means we cannot trust any of our sensors.

We could consider that, physically, the `MeasureVoltage` function could never
exceed a given threshold. But then, we should have already inserted some
defensive programming and trimmed the limits to reasonable levels.

For now, we will have to "weaken" our attacker: we will impose that, for
some arbitrary reason, the voltage sensors of units 3 and 4 (our satellite
has 4 such units) are immune to corruption (e.g., they are protected by an
anti-evil-AI shield).

We will "simulate" this by adding an annotation to the `MeasureVoltage`
function, in the `case channel_1_e:` switch branch, before the assignments.
This annotation will claim that `AD_voltage_parameters.unsigned_ADC` is not,
in fact, tainted: `//@ admit !\tainted(AD_voltage_parameters.unsigned_ADC);`
(the `admit` annotations tells Frama-C "from now on, assume this is valid").

Use your code editor to add such annotation, re-run Frama-C and re-open Ivette.

See if the `//@ check !\tainted` annotation is now valid.

If necessary, add an additional `admit` annotation near the previous one,
to ensure the required property is untainted.

(Remember that each such annotation implies adding costly EMP shields to our
sensors; but what is the cost of freedom?™)
