## Task 3: Unknown and Invalid Properties

When using Eva to find issues in the code, we are mostly concerned with what
Frama-C calls *properties*: logical statements associated to code locations.
In particular, *unknown* and *invalid* properties, that is, those that Eva
could not prove, and which indicate possible problems in the code.

Open `3.c` in Ivette with Eva. Open the Properties view.
In the right-hand side of the Properties panel (bottom-center of the screen),
there are several arrows to fold/unfold categories. In the Status category,
unfold it and uncheck "Valid" and "Valid under hyp.".

You should have 2 remaining properties to check. Clicking on a property centers
the AST and source code on the statement.

One of these properties can be proven given enough precision.

### Task 3.1. Customizing the view

With drag-and-drop, you can add a *component* from the right-hand sidebar.
Components have a cube icon next to them and are grouped either under
"Frama-C Kernel" or "Frama-C Plug-ins".

Get the *Eva Values* component and put it in the bottom-center part of the screen.
You should have a new panel. Now click on a property in the Properties panel.
The *Eva Values* panel will show the evaluation for the property itself. Clicking
on any expression in the AST will show the value inferred by Eva for that
expression.

### Task 3.2. Improving precision

For both properties, check the values of the variables in their expressions (if
there are any). Note that these values are *over-approximations*.

Now re-run Eva with some values for `-eva-precision`. Try to get the smallest
precision that removes one of the properties. In this toy example, even the
maximum value will run near-instantly, but analysis time can grow exponentially.

Once the property disappears, go to the statement where it was before, and check
the Eva Values for the associated variable.

**Explanation**: with extra precision, Eva avoided or improved upon its *widening*
operation (necessary to ensure termination of the analysis), thus reaching a much
smaller value that is still correct. This, in turn, prevents some possible
undefined behaviors from happening.

## Task 4. Annotations

In the AST panel, we see that Frama-C added *annotations* to the code. These
special comments do not exist in the source code. In our test program, we have
function preconditions (`requires`) and assertions (`assert`).

An annotation such as
`assert Eva: signed_overflow: 2147483647 + 1 ≤ 2147483647;`
can be interpreted as:

> The Eva plug-in _needs_ to assert that this signed overflow does NOT occur.
> It was not able to prove it.
> Eva emits the assertion and _assumes_ that it holds, before continuing its
> analysis.

Each property has a circle in the left-hand side of the AST, which resumes its
status. In our test program, it can be:
- Green: Eva (or someone else) proved this is true. You can ignore it.
- Orange: Eva did not prove it, or proved it _partially_.
  Someone else (another plug-in) needs to prove it.
- Red: Eva (or someone else) knows this is **false**!
  There is a bug in the code, or some problem in the parametrization.
- Black: this property is unreachable to Eva ("dead code").

A black circle is neither intrinsically "good" nor "bad". It simply means the
analysis did not reach it.

Compare the output of the compiled program execution with the analysis made by
Eva. What can be said about the "NON TERMINATING FUNCTION" message that Eva
emits in its log (either in the command line, or in the Console view in Ivette)?

## Task 5: Forcing GCC/Clang to agree with Frama-C

Frama-C is following the C standard to the letter. To see this in GCC/Clang,
recompile `3.c` with option `-ftrapv`, which causes signed overflows to result
in a trap during execution. See what happens.

Note: GCC/Clang perform several optimizations and analyses even without option
`-O`. You may need to change the code to prevent the `INT_MAX+1` from being
optimized away. For instance, you can replace this line:

```c
  printf ("%d -> %d\n", INT_MAX+1, mylog2(INT_MAX+1));
```

With the following code:

```c
  int v = INT_MAX;
  v++;
  printf ("%d -> %d\n", v, mylog2(v));
```

This increases the likelihood that GCC/Clang will trap during execution.
